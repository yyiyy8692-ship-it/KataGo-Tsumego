**批改用 max_visits 建议 ≥3000**（800 不够区分手筋3 的 G6 与 F3）。

手筋3 的 G6 与 F3 目差仅 0.4，说明该题在引擎眼里接近双解。用"唯一正解"
判孩子对错会把合理答案判错，必须设"双解/存疑"档。

### 2.3 排除的怀疑：G 列是不是多检了一列

三道手筋题的引擎最佳手都落在 G 列（最右列），怀疑网格右边多检一条线。
实测：格距 75px，7 列跨度 452px，左右边距对称（46 / 44 px）——**网格正确，
没有多检**。G 列是贴墙的一路线，手筋答案落在一路线是真实的。

## 三、卡点：题型不匹配

PDF 文字写明 **「全部黑先」**，题型为「全局题1/2/3」+「手筋题1/2/3」。

现有 `grader/grade.py` 只支持 4 种**死活题**型：

```
B_kill / B_live / W_kill / W_live   （黑先杀白 / 黑先做活 / 白先杀黑 / 白先做活）
```

且结尾强制走死活裁决 `_verdict_from_ownership()`——用 ownership 平均归属判
目标棋群死活。这个判据对这份题无效：

- **全局题**是 19 路实战局面（60~105 子），不是空枰死活题。第1题 208 子、
  最佳手 R1（一路官子），属**官子型全局题**，没有"某块棋死活"这个目标。
- **手筋题**的目标是吃子 / 连通 / 破空，同样不是做活杀棋。

强套死活裁决会输出无意义的"活/死/不明"，并触发假警报。

---

## 四、方案：新增非死活题型的批改分支

不做死活裁决，改为 **手顺比对 + 目差损失分档**。

### 流程

识别局面 → 引擎分析（黑先，≥3000 visits）→ 逐手比对（排名 + 目差损失）→ 分档评级

### 分档阈值（建议，可按教学需要调）

| 目差损失 | 评级 |
|---|---|
| ≤ 0.5 目 | 正解 |
| 0.5 ~ 2 目 | 好手 |
| 2 ~ 5 目 | 疑问手 |
| > 5 目 | 恶手 |

### 双解规则

引擎 top1 与 top2 目差 < 1 目 → 标记双解，孩子下任一首选都算对。
（手筋3 属此类。）

### 待确认的两个决策

1. **全局题的判定标准**：整盘实战局面下，"对错"是否仍用目差？教学上全局题
   重大局观，目差可能只是参考。可选：只报目差损失不判对错 / 与手筋题同样分档。
2. **先做哪个版本**：
   - 轻量版：只出正解 + 变化图 + 讲解，不需要录入孩子的下法（立刻可用）
   - 完整版：含孩子答案录入与逐手批改
